# Raw Bible passage retrieval: exploratory comparison

2026-11-06. This replaces the earlier graph lookup as evidence about raw text. The corpus is the 31,102-verse KJV SQLite file from [midvash/bible-data](https://github.com/midvash/bible-data) at commit `9586bd8228a747962df1ee8692730422fb7eb2ec`; file SHA-256 `e595b86c6e2a4f1d8b8ec141ff5a4cef049e2e39a126e48e868342dd4a313849`. Questions and one designated answer passage per question are from [BibleQA](https://github.com/helen-jiahe-zhao/BibleQA), commit `fd031b365a2b8e3d5a7cd15a797d2f5c58500d19`, file `data/bible_qa/bible_qa_list_3_kjv.json`, SHA-256 `0e02766ad2e7c1a9857f3069fa9237b8cc51742054a3d5ac81ba1940f3cc07b5`. Check source rights and attribution before redistributing the question dataset.

The BibleQA designated passage was normalized and matched to a unique KJV verse before sampling; questions containing a numeric verse reference or a double quotation mark were removed. A fixed seed (20261106) selected 160 from 740 eligible rows. The initial prototype used a different selection before applying the no-direct-quote filter; this run was then frozen before inference. The question types are diverse but drawn from one trivia dataset; it is not an exhaustive Biblical QA test. BibleQA gives only one designated verse here. Other verses may be valid answers, so **failure to retrieve that particular verse is not proof that a system failed to find an answer**. Metric is designated-passage recall, not answer accuracy.

Each document is one original verse, with its text unaltered. SQLite FTS5 indexes the actual verse text; XERJ full-text search indexes the same verses. The same deterministic list of non-stopword query terms is derived from the question alone, never from its gold answer or verse. SQLite OR-matches terms; XERJ gets the same OR terms. Each retrieves five verses. XERJ uses its search engine here, not Query-1. XERJ and SQLite use different implementations and network paths.

For the Seb reranker, each of the five SQLite hits is independently assessed against the question by Seb v2 with a yes/no relevance judgment. Hits are ordered by the returned probability; no answer generation or multiple choice is involved. This makes 800 paid judgments for 160 questions. There are no gold references or answer candidates in the model inputs. `verify.py` checks all 800 successes, order, gold alignment and costs.

| Method | Designated verse at rank 1 | In top 5 |
|---|---:|---:|
| SQLite BM25 | 25/160 | 52/160 |
| XERJ full-text search | 25/160 | 52/160 |
| SQLite BM25 + Seb reranking | 42/160 | 52/160 |

Seb cannot recover a designated verse that BM25 did not retrieve. Median local BM25 retrieval was 0.643 ms; XERJ search HTTP client wall was 0.382 ms. These are different implementations and single-run timings, not a load test. Seb median per-passage API time was 60.6 ms; that is **not** the total latency of reranking five passages. Seb used 118,352 metered input tokens and 2,485,392 cost-nanos ($0.002485392) for 160 questions, i.e. $0.0155337 per 1,000 questions for the five relevance calls, excluding BM25 compute, network and hosting. At identical workload and prices this extrapolates to $1.55/100K, $15.53/1M and $155.34/10M questions; these are arithmetic, not measured throughput.

Indexing: SQLite indexed raw verses in 77.0 ms wall / 72.3 ms CPU; XERJ full-text ingestion plus refresh took 1.50 s wall, including the local HTTP bulk client. Data reading and client construction are not equivalent between those paths; CPU for XERJ was not measured. Both are one-off local timings; no full-stack cost is claimed.

XERJ Query-1 is a different path from XERJ full-text search. To check raw-only behavior, all 31,102 verse documents were also written into a fresh `/_facts/rawonly` namespace with **no extracted facts**. Query-1 returned `UNKNOWN` on all 160 questions. This matches the [vendor quickstart](https://github.com/xerj-org/xerj/blob/main/docs/MODEL_QUICKSTART.md): documents are source evidence, but facts must be supplied for the facts model to answer. This is not a test of Query-1 after fact extraction, and the costs of extracting and verifying typed facts from raw KJV text remain unmeasured. It is also not evidence that XERJ full-text search cannot retrieve raw passages.

## Files and reproduction

`questions.json` stores frozen questions, IDs and SQLite hits; `xerj-results.jsonl`, `facts-results.jsonl`, `seb-0.json` through `seb-7.json` are raw responses, and `reranked.json` records scores and rank order. `summary.json` is regenerated by `python3 verify.py`.

Download both pinned sources to `../data/kjv.sqlite` and `../data/bibleqa.json`, verify hashes, and start XERJ rc.101 with its model bundle on local port 19291 with a fresh data directory. With a fresh `bible.sqlite`, run `python3 bench.py prepare`, `python3 bench.py xerj-index`, `python3 bench.py xerj-ask`, `python3 bench.py facts-raw-index`, and `python3 bench.py facts-raw-ask`. Send one state per question/hit pair, in row and hit order, in eight batches of 100 to Seb v2 `seb_batch_decide` with the `noul` instruction: `Does the passage provide information that helps answer the question? Answer yes only if it is relevant to answering the specific question.` Store each response as `seb-0.json` through `seb-7.json`; sort the five by returned `noul` descending, retaining retrieval order on ties. Run `python3 verify.py`.

## XERJ-only autoindex check

Following the request to use only XERJ-provided ingestion tools, rc.101 `xerj autoindex` was run with the default graph path, four workers and a fresh isolated data directory against the unmodified KJV SQLite file. The official CLI reported 31,102 indexed records, no junk, 3.7 seconds internal wall (3.94 seconds subprocess wall), and zero graph edges. `_cat/indices` confirmed 31,102 documents in `kjv-verses`. The CPU model reported `loaded`, four threads, with counting ready. Its `/_facts` endpoint returned an empty namespace list. A full-text search in `kjv-verses` returned HTTP 200; a Query-1 request to `/_facts/kjv-verses/_ask` returned HTTP 404: `no facts namespace [kjv-verses]`. Evidence: `official-autoindex.json`, `official-query-check.json`. Query-1 cannot be evaluated on this index until facts are created; this run did not perform or time any external fact extraction. XERJ full-text search is functional but is not the Query-1 model.

The latest released version was rc.101 at this check. The main-branch quickstart documents a post-rc.101, unreleased `autoindex --facts` for structured table columns; the shipped rc.101 autoindex help does not advertise that flag. Converting table cells to facts is distinct from extracting event and relationship facts from narrative verse text.
